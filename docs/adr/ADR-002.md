# ADR-002: Hub-Spoke Network Topology

**Date:** June 2026  
**Status:** Accepted  
**Author:** Moshood Adisa

## Context

The azure-landing-zone platform requires a network architecture that supports
multiple workloads with independent lifecycle and ownership, enforces
centralised routing and security policy, and can scale to additional landing
zones without restructuring existing infrastructure.

The platform operates without Azure Firewall due to the £10/month budget
constraint (~£150/month). Inter-spoke traffic control is required despite
this constraint. The architecture must document the production pattern even
where cost requires a simplified deployment.

## Decision

A hub-spoke topology is implemented across three VNets:

- `vnet-hub` (10.0.0.0/16) — platform-owned. Houses shared services,
  Application Gateway, and NVA subnets. All inter-spoke traffic routes
  through here.
- `vnet-workloads` (10.1.0.0/16) — workload landing zone. Houses compute,
  containers, and AKS subnets.
- `vnet-data` (10.2.0.0/16) — data landing zone. Subnets provisioned
  on demand for PaaS and Private Endpoints.

All VNet peerings are bi-directional. Spoke-to-spoke traffic is not
transitive through peering alone — cross-spoke traffic is forced through
the hub NVA via UDRs on both spoke route tables, preventing asymmetric
routing.

The NVA subnet carries no NSG by design. Traffic policy on that subnet
is enforced at the OS level on the NVA appliance. NSG evaluation before
NVA forwarding would interfere with routing decisions.

AKS internet egress uses NAT Gateway rather than the NVA, isolating the
cluster control plane path from a single point of failure on the NVA.

Adding a new workload landing zone requires a new spoke VNet and peering
pair — no changes to existing infrastructure.

## Alternatives Considered

**Flat VNet with subnets per workload** — all workloads share a single
VNet, separated by subnets and NSGs. Rejected. Workload teams would need
access to platform networking to add subnets. Address space conflicts
become likely as workloads grow. No clean ownership boundary between
platform and workload.

**Azure Virtual WAN** — Microsoft-managed hub-spoke with automatic route
management. Rejected. Cost is prohibitive at this scale — Virtual WAN
hubs start at ~£150/month before traffic charges. The pattern is noted
as the production recommendation for organisations at enterprise scale.

**Azure Firewall instead of NVA** — managed firewall service in the hub.
Rejected on cost grounds (~£150/month). The NVA pattern achieves the
same routing outcome. The production alternative is documented: replace
the placeholder NVA with Azure Firewall, update route tables to point
to the Firewall private IP, and configure Firewall Policy rules to
replicate the OS-level policy currently on the NVA.

## Consequences

**Positive:**

- Spoke VNets are independently managed — workload teams control their
  address space, subnets, and NSGs without touching platform networking
- Inter-spoke traffic is inspectable and controllable at the NVA
- The platform boundary is enforced at the network layer, not just by
  convention
- New workload landing zones are additive — existing infrastructure is
  unchanged

**Negative:**

- NVA represents a single point of failure for inter-spoke traffic.
  Mitigated by design: AKS internet egress bypasses the NVA via NAT
  Gateway, limiting the blast radius of an NVA failure to cross-spoke
  traffic only
- Route tables on both spokes must be kept consistent — asymmetric
  routing is possible if UDRs are misconfigured. Enforced by managing
  all UDRs in a single `udr.tf` file within platform/connectivity
- Azure Firewall is the production recommendation for this pattern.
  The cost trade-off is documented and the implementation path is known
