# ADR-003: OIDC Workload Identity Over Service Principal Secrets

**Date:** June 2026  
**Status:** Accepted  
**Author:** Moshood Adisa

## Context

The azure-landing-zone platform requires GitHub Actions workflows to
authenticate to Azure for Terraform plan and apply operations. A
credential strategy was required that could support multiple repositories
with distinct permission scopes, eliminate the operational overhead of
secret rotation, and prevent credential exposure in GitHub repository
settings or workflow logs.

The platform manages sensitive infrastructure — networking, identity, and
governance — where a leaked credential with Contributor scope would
represent a significant security incident.

## Decision

All GitHub Actions workflows authenticate to Azure via OpenID Connect
federated credentials. No service principal secrets are stored in GitHub.

The authentication flow works as follows:

1. The GitHub Actions runner requests a short-lived JWT from GitHub's
   OIDC provider
2. The JWT is exchanged with Azure AD for an access token scoped to
   specific resources
3. Azure AD validates the JWT against the federated credential subject
   claim registered on the service principal
4. A short-lived access token is returned, valid only for the duration
   of the workflow run

Each repository has a dedicated service principal managed by
`platform/identity/github-oidc`. Two federated credentials are
configured per repository, scoped to distinct GitHub event types:

- `github-main-branch` — subject: `repo:<org>/<repo>:ref:refs/heads/main`
  Used by apply workflows triggered on merge to main
- `github-pull-requests` — subject: `repo:<org>/<repo>:pull_request`
  Used by plan workflows triggered on pull requests
- `github-environment-production` — subject:
  `repo:<org>/<repo>:environment:azure-production`
  Used by apply workflows running in the azure-production environment

A token issued for a PR plan job cannot authenticate an apply — the
subject claims do not match. This constraint is enforced by Azure AD,
not by workflow logic, and cannot be bypassed by workflow modification
alone.

All service principals and federated credentials are managed in Terraform
via `for_each` over a `repos` variable. Adding a new workload repository
requires a new entry in `terraform.tfvars` and corresponding RBAC
defined in `rbac.tf`.

## Alternatives Considered

**Service principal client secret stored in GitHub secrets** — a
long-lived secret generated on the service principal and stored as a
GitHub Actions secret. Rejected. Secrets require rotation, carry
expiry risk, and represent a persistent credential that can be extracted
from GitHub settings or accidentally logged. A leaked secret with
Contributor scope on platform resource groups represents an unacceptable
blast radius.

**Service principal certificate** — certificate-based authentication
stored as a GitHub Actions secret. Rejected for the same reasons as
client secrets. Certificates are longer-lived than desired and still
require rotation management.

**Managed Identity on a self-hosted runner** — a VM or container runner
with an Azure Managed Identity attached. Rejected. Self-hosted runners
introduce infrastructure management overhead incompatible with the
programme's time and budget constraints. GitHub-hosted runners are
ephemeral and carry no persistent identity.

## Consequences

**Positive:**

- No credentials stored anywhere — nothing to rotate, nothing to leak
- Subject claim scoping means PR workflows cannot trigger applies,
  enforcing separation of plan and apply at the identity layer
- All service principals and their permissions are declared in Terraform
  and version controlled — the identity model is auditable and
  reproducible
- Adding a new workload repository is a controlled, platform-gated
  operation

**Negative:**

- The github-oidc module requires Microsoft Graph permissions to manage
  AAD application registrations. This exceeds what an automated CI
  pipeline should hold. The module is therefore excluded from automated
  drift detection and requires manual apply by an operator with
  sufficient Graph permissions. This is documented in the platform
  runbook.
- Federated credential subject claims must exactly match the GitHub
  Actions context. A mismatch produces a cryptic authentication error
  that is difficult to distinguish from a permissions problem without
  understanding the OIDC exchange mechanism. Subjects must be verified
  carefully when adding new repositories or changing workflow triggers.
- Recovery from accidental resource destruction in this module requires
  reconciling Terraform state against configuration before applying.
  This occurred during the Phase 0 audit when an apply without plan
  review destroyed live federated credentials and RBAC assignments.
