# ADR-004: Terraform Provider Pinning to Exact Versions

**Date:** June 2026  
**Status:** Accepted  
**Author:** Moshood Adisa

## Context

The azure-landing-zone platform uses Terraform providers from HashiCorp
and third-party sources — azurerm, azuread, and random. Provider versions
are published independently of Terraform core and may introduce breaking
changes, altered resource behaviour, or new provider defaults between
minor and patch releases.

The platform runs across two execution contexts: local developer
environments and GitHub Actions CI runners. Without explicit version
constraints, each context may resolve different provider versions,
producing inconsistent plan output and making clean-deploy
reproducibility impossible to guarantee.

The programme handshake requires that `terraform plan` on
azure-landing-zone produces zero errors and zero unexpected changes from
a clean checkout. That criterion cannot be met if provider resolution is
non-deterministic.

## Decision

All Terraform providers across all platform modules are pinned to exact
versions using the `=` constraint operator:

```hcl
required_providers {
  azurerm = {
    source  = "hashicorp/azurerm"
    version = "= 3.110.0"
  }
  azuread = {
    source  = "hashicorp/azuread"
    version = "= 2.53.1"
  }
}
```

The `.terraform.lock.hcl` file is committed to the repository for every
module. The lock file records the exact provider version and cryptographic
hashes for all required platforms, ensuring that `terraform init` on any
machine or CI runner installs exactly the same provider binary.

Provider version upgrades are a deliberate, explicit action — update the
version constraint, run `terraform init -upgrade`, commit the updated lock
file, and validate the plan before merging.

## Alternatives Considered

**Approximate constraint (`~> X.Y`)** — allows patch-level upgrades
within a minor version. For example, `~> 3.110` would permit any 3.110.x
release. Rejected. The azurerm provider has a history of introducing
behaviour changes and new provider defaults in patch releases. The
`soft_delete_enabled` default change on `azurerm_recovery_services_vault`
observed during the Phase 0 audit is a direct example — an implicit
provider default changed between versions, causing unexpected drift on
every plan until the attribute was made explicit. Approximate constraints
make this category of problem harder to detect and attribute.

**Minimum version constraint (`>= X.Y.Z`)** — allows any version at or
above the specified minimum. Rejected. This provides no upper bound and
offers no reproducibility guarantee. Two engineers running `terraform init`
on the same codebase at different times may install different provider
versions and produce different plan output.

**No version constraint** — always resolves the latest available version.
Rejected immediately. Latest versions introduce breaking changes without
warning. This approach is incompatible with any serious infrastructure
management practice.

## Consequences

**Positive:**

- `terraform plan` produces identical output on any machine or CI runner
  that initialises from the same commit, satisfying the clean-deploy
  reproducibility requirement in the programme handshake
- Provider behaviour changes are opt-in — a deliberate upgrade action,
  not a silent side effect of a new release
- The lock file provides cryptographic verification of provider binaries,
  preventing supply chain substitution attacks
- Unexpected drift caused by provider default changes is eliminated —
  any drift is attributable to configuration or infrastructure change,
  not provider behaviour

**Negative:**

- Provider upgrades require deliberate action and a plan validation
  cycle. Security patches in providers are not applied automatically.
  Mitigated by treating provider upgrades as a scheduled maintenance
  task rather than a reactive fix.
- Lock files must include hashes for all execution platforms — linux_amd64
  for CI runners and darwin_amd64 for local macOS development. A lock
  file generated on one platform only will cause hash mismatch errors on
  the other. Resolved by running `terraform providers lock
-platform=linux/amd64 -platform=darwin/amd64` when updating providers.
