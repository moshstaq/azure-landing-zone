# ADR-001: Per-Module Azure Blob Storage for Terraform Remote State

**Date:** June 2026  
**Status:** Accepted  
**Author:** Moshood Adisa

## Context

The azure-landing-zone platform manages multiple infrastructure domains —
connectivity, management, governance, and identity — each with independent
lifecycle and deployment cadence. A state storage strategy was required that
could support concurrent development, limit blast radius from failed
operations, and protect state files from accidental loss or corruption.

The platform operates under a £10/month budget constraint across both clouds,
ruling out managed state backends that carry per-user or per-workspace costs.

## Decision

Each platform module owns an isolated state file stored in Azure Blob Storage
within a dedicated storage account (`sttfstate7tcl`) in `rg-tfstate`. State
files are namespaced by module:

- `platform-connectivity.tfstate`
- `platform-management.tfstate`
- `platform-governance.tfstate`
- `platform-github-oidc.tfstate`

Cross-module references use `terraform_remote_state` data sources scoped to
specific outputs. No shared or monolithic state file exists.

The storage account is protected by three independent mechanisms:

- Blob versioning — recovers overwritten state on every apply
- Container soft delete — recovers accidentally deleted containers within
  7 days
- CanNotDelete resource lock on `rg-tfstate` — survives Contributor-level
  access

## Alternatives Considered

**Monolithic state file** — a single state file for all platform modules.
Rejected. Any Terraform operation locks the entire platform. A corrupted or
lost state file affects all infrastructure simultaneously. Blast radius is
unacceptably wide.

**Terraform Cloud** — managed remote state with built-in locking and audit
trail. Rejected. Introduces a per-seat cost incompatible with the programme
budget constraint. Also introduces an external dependency on a third-party
service for a portfolio that is otherwise self-contained on Azure and AWS.

**Local state** — state files committed to the repository. Rejected
immediately. State files contain sensitive resource IDs and outputs. Committing
them to a public repository is a security violation. Local state also makes
CI/CD impossible.

## Consequences

**Positive:**

- A failed or corrupted state file in one module cannot affect any other
  module
- Modules can be planned and applied independently without contention
- State is protected against accidental deletion and overwrite at the storage
  layer
- Cost is effectively zero — blob storage at this scale costs under £1/month

**Negative:**

- Cross-module references require `terraform_remote_state` data sources,
  which introduces an explicit apply ordering dependency — management before
  connectivity, connectivity before identity
- State lock conflicts can occur if CI runners crash mid-operation without
  releasing blob leases. This occurred during the Phase 0 audit and required
  manual lease breaking and blob re-upload to recover. Mitigated by ensuring
  CI workflows release locks on failure via `continue-on-error` handling.
